# Project Architecture Template

这是一份通用的中大型项目架构模板，适合在项目启动、中期重构、收官阶段反复使用。

使用方式：
- 新项目启动时，先把这份模板复制一份，按项目实际情况填写。
- 项目中期开始变复杂时，用它检查是否已经出现“协议分叉、职责重叠、过度自由、过度 agent 化”等问题。
- 项目收官时，用它做系统性收口，确保项目能讲、能改、能维护。

## 6. Layering

把系统拆成层，不要把所有能力混在一起。

建议的最小分层：
- 稳定层：状态、schema、manifest、renderer、verifier、persistence
- 策略层：planner、scenario policy、tone policy、asset policy
- 生成层：文案、区块选择、局部编辑、动态输出
- 展示层：前端 UI、调试面、交互动作
- 兼容层：新旧协议转换、迁移期 adapter

## 9. LLM / Agent / Workflow Decision

每一块都先判断它属于哪种形态。

### 适合普通 LLM
- 单次理解
- 单次改写
- 单次结构化输出

### 适合 Agent
- 需要自主决策
- 需要选工具
- 需要在多动作之间做选择

### 适合 Workflow
- 阶段稳定
- 顺序稳定
- 中间状态要被显式消费

### 适合纯函数/规则
- 校验
- 编译
- 渲染
- 转换
- 状态合并

## Fast Self-check

每次要做较大改动前，先问自己：
- 这个系统真正处理的对象是什么？
- 哪个数据结构是唯一真相源？
- 这件事该交给代码，还是交给模型？
- 这次改动是在统一系统，还是让系统更分叉？
- 如果用户输入范围扩大 10 倍，这里会先崩吗？

---

## Recommended Order

以后做中大型项目，建议按这个顺序推进：
1. 定一句主故事
2. 定核心对象
3. 定主协议和 schema
4. 定 state
5. 做单一真相源
6. 做职责拆分
7. 再决定哪里用 LLM
8. 再决定哪里用 agent
9. 再决定是否需要多 agent
10. 中后期开始系统性收口

---

## Closing Principle

先定对象和协议，再让模型服务系统；不要让系统跟着模型跑。
