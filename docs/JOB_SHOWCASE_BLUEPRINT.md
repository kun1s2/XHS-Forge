## 1. 项目定位

这个项目更适合作为“类小红书智能内容工作台”的求职展示项目，而不是一个追求全量覆盖的生产系统。

展示重点应该是：

1. 用户可以用自然语言生成和修改笔记
2. 系统支持长期追踪、回滚和分支创作
3. 对热点、争议和时效信息有处理能力
4. 通过缓存和预热机制降低 Agent 与搜索成本
5. 打开项目后可以直接进入 3 条一键演示业务线

不应该继续追求：

1. 做太多零散垂类
2. 为所有组件和边角场景做生产级覆盖
3. 把故事讲成“一个很复杂的流水线”

更适合的面试叙事是：

“我做了一个面向社交内容创作的 Agent IDE。它能持续维护一张可编辑的笔记状态，让用户通过自然语言反复修改，并且支持热点缓存、版本回滚和分支创作。”

## 2. 建议只讲三条业务线

### A. 数码评测 / 热点种草

推荐作为主故事线。

为什么：

1. 最容易展示热点追踪、实时搜索、争议对立
2. 最容易展示事实增强、投票卡、对比卡、雷达图
3. 最容易讲缓存价值，因为热点流量集中、重复请求多

适合展示的能力：

1. 热词缓存与后台预热
2. 对立观点生成
3. 结构化组件渲染
4. 自然语言二次修改

### B. 旅行探店 / 城市探索

推荐作为第二条故事线。

为什么：

1. 最容易展示位置、天气、路线这类外部信息融合
2. 适合展示多源工具调用与时效信息
3. 和数码评测形成明显对比，能证明架构不是只会做一个垂类

适合展示的能力：

1. 地点与天气类事实补全
2. 旅行叙事与攻略化重写
3. 长图文布局
4. 持续编辑同一篇笔记

### C. 日常分享 / 长期陪伴记录

推荐作为第三条故事线。

为什么：

1. 最适合讲“长期线程、checkpoint、回滚、分支”
2. 最适合讲上下文工程和创作者人设保持
3. 不依赖重事实搜索，正好补足前两条业务线

适合展示的能力：

1. 长期线程记忆
2. 组件级回滚
3. 分支创作
4. 风格和情绪重写

## 3. 当前最合理的架构判断

你当前的项目方向是对的，但之前的问题在于“能力太散，故事太宽”。

对求职项目来说，更好的讲法是：

`intent -> editor runtime -> verifier -> render`

配套两个基础设施亮点：

1. `hot cache / trend prewarm`
2. `checkpoint / rollback / fork`

也就是说，真正该被当成亮点的不是“有很多 Agent”，而是：

1. 有一个持续维护状态的 Note Editor
2. 有一个能处理热点与争议的事实层
3. 有一个能让用户回滚和分叉的持久化工作台

## 4. 建议你在面试里强调的亮点

### 亮点 1：自然语言不是一次性生成，而是可持续编辑

用户不是“生成完就结束”，而是可以持续说：

- 保留标题，重写第二段
- 把投票换成雷达图
- 整体改成灰蓝风格
- 删掉参数卡

这比单次生成更像真实产品。

### 亮点 2：状态是可持久化、可回滚、可分支的

你项目里已经有：

1. checkpoint
2. workspace 恢复
3. 组件级 rollback
4. fork thread

这非常适合被讲成“创作 IDE”而不是“聊天机器人”。

### 亮点 3：热点内容有缓存和预热

对于社交平台，热点内容是强时效、强重复请求的。

你现在这套设计可以讲成：

1. 用户提问驱动热词发现
2. Redis/ZSet 风格缓存做热点排行
3. 后台预热知识包
4. query + selected_element 级缓存减少重复 Agent 成本

### 亮点 4：争议内容不是 bug，而是业务特性

社交平台很多内容天然是对立的。

所以你项目里的：

1. controversy sniffer
2. battle report
3. PollBlock / VersusCard / RadarChartBlock

可以被讲成“针对高互动内容设计的争议感知生成机制”。

## 5. 当前仓库里建议保留与建议淡化的部分

### 建议保留

1. `Note Editor V2`
2. `workspace` / checkpoint / rollback / fork
3. `trend cache` / `trend pipeline`
4. 数码评测、旅行探店、日常分享三条场景
5. 结构化组件渲染

### 建议淡化

1. 太多旧的自由发挥式流水线节点
2. 过多的“万能场景”叙事
3. 不在主故事线里的 pet 等支线场景

不是说这些一定要删除，而是在面试叙事里不要让它们抢主线。

## 6. 推荐 Demo 顺序

前端现在已经适合补一个统一的 demo 入口:

1. 通过 `/workspace/showcase/profiles` 拉取策展好的 3 条业务线
2. 每条业务线提供：
   - 一键演示
   - 改文案 prompt
   - 改主题 prompt
   - 分叉 prompt
   - 可展开的面试手卡（demo script + talking points）
3. 一键演示时同步切换推荐创作者人设
4. 这样面试时不需要临场想 prompt，打开页面就能开始讲

### Demo 1：数码评测

1. 生成一篇热点数码笔记
2. 把投票换成雷达图
3. 把整体改成灰蓝风格
4. 展示 checkpoint 和分支

### Demo 2：旅行探店

1. 生成一篇旅行/探店笔记
2. 补地点或天气感
3. 展示多轮修改仍保持同一页面

### Demo 3：日常分享

1. 生成一篇生活记录
2. 多轮修改语气与结构
3. 回滚到旧版本
4. 从旧版本分叉一个新分支

## 7. 结论

对求职项目而言，你当前最需要的不是“更多 Agent”，而是：

1. 更窄的业务面
2. 更清晰的面试故事
3. 更能体现产品感的功能闭环

当前最推荐的讲法就是：

“一个支持长期追踪、热点增强、可回滚分支的社交平台笔记生成与编辑工作台。”

## 8. 隐藏式展示入口

如果你不希望面试官在普通界面里直接看到 `showcase` 入口，可以保持默认关闭。

前端现在支持编译期开关：

1. 默认值是 `VITE_ENABLE_SHOWCASE=false`
2. 只有在本地 `.env.local` 或构建环境里显式设置成 `true` 时，才会显示 showcase 卡片和面试手卡
3. 关闭时前端不会去请求 `/workspace/showcase/profiles`

示例：

```bash
cd /root/XHS-Forge/ai-frontend-ide
cp .env.example .env.local
echo "VITE_ENABLE_SHOWCASE=true" >> .env.local
```
